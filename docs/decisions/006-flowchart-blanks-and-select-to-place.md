# 006 — Fill-in-the-blanks: derived blanks, select-then-place instead of drag, proportional hints

**Date:** milestone 14b
**Status:** accepted — no locked section reopened; D31, D32, D34 are all unchanged in outcome,
only in mechanism (the same relationship 14a's `decisions/005` already established for D35)
**Narrative version:** `docs/DESIGN_RATIONALE.md` §38

## What changed

Three things §9 left unspecified about the flowchart exercise are now settled:

1. **Which nodes get blanked, and what the bank holds** (`src/game/flowchartBlanks.ts`). Blanks
   are ranked by teaching value — branch conditions, then loop headers, then `io`, then
   `process` — never terminals, `def` signatures, or jump exits. The bank holds exactly the
   blanked labels, shuffled; no distractor cards.
2. **Hint level is a proportion of the chart, not a fixed count.** Easy pre-fills roughly 2/3,
   medium 1/3, hard none.
3. **The interaction is select-then-place, not drag.** §9's structure diagram says "drag cards to
   complete the flowchart"; the shipped exercise instead has the learner click a card to pick it
   up and click a blank to place it, with an identical keyboard path (Space to pick up, arrows to
   move between blanks, Space to place, Escape to cancel).

## Why it changed

**Blanks ranked by teaching value, because the point is testing understanding of control flow,
not memorising which shape came first.** A branch condition is the thing a learner most needs to
reconstruct; an assignment inside a loop body is comparatively mechanical. Terminals and `def`
signatures stay as permanent scaffolding — without them the chart has no readable skeleton to
orient against — and a jump's label ("leave the loop") is this renderer's own wording (m14a
finding 1), not the author's, so blanking it would test nothing about the program.

**No distractor cards, because D32 says "how many cards start pre-filled," not "how large the
bank is."** N blanks, N cards is the literal reading of that sentence and stays free of
authoring — a distractor generated by mutating a real label (flipping a comparison, shifting a
bound) is still, in effect, a second hand-tuned artifact per program, which is exactly what D34
argues against paying for. The real cost — the last card is always free by elimination — is
recorded as a stated limitation in `docs/GAME.md`, not hidden.

**Proportional hint levels, because a fixed count doesn't scale with the chart.** The corpus's
own blankable-node counts range from 2 (`functions-easy`, `recursion-medium`) to 10
(`bubble-sort-hard`), measured directly before this ratio was chosen (`docs/GAME.md`'s own
table). A fixed count of "3 blanks at medium" would be trivial on the 10-node chart and
impossible on the 2-node one. `ceil(n/3)` / `ceil(2n/3)` / `n` keeps easy and medium meaningful
at every size, and makes hard mean "reconstruct the whole thing" — which is what hard should mean
— rather than an arbitrary number.

**AC-9.21's honest form is non-increasing, not strictly decreasing, for every program.** A
2-blank chart cannot distinguish medium from hard: `ceil(2·2/3) = 2 = 2`, so both levels correctly
pre-fill nothing. Weakening the criterion's test to match this, rather than forcing a rule that
manufactures a fake distinction on a 2-node chart, is the same "measure first, then write the
rule against the real numbers" discipline `decisions/003`'s pre-milestone audit already commits
this project to — verified over all 24 real corpus programs, not asserted on a handful of
examples.

**Select-then-place, because a bank→blank drag has no reliable geometry to drag onto.** 13b's
`BlockList.tsx` drag (`Reorder.Group`) reorders *within* one list — there is no separate drop
target, so framer-motion's own layout math handles it entirely. Placing a card into a specific
blank needs real drop-target hit-testing, and those targets live inside nested flex columns that
**reflow every time a slot fills** (an empty dashed placeholder and a filled label are different
widths) — every blank's bounding box would need re-measuring after every single placement. AC-9.17
already established that this project treats keyboard as a full peer to pointer input, not a
fallback bolted on afterward; one mechanic that is byte-identical for mouse, touch and keyboard
is strictly better engineering than two paths (a real drag gesture, plus a separate keyboard
affordance) that can drift apart from each other over time. This is recorded here as a `v2
correction (m14b)` on §9's own wording, not a silent substitution.

## Which sections this invalidates

None. §9's flowchart paragraph gets an inline `v2 correction` for the "drag cards" wording;
D31 ("generated from the parsed program"), D32 (two independent settings) and D34 (nothing
hand-authored beyond the program) are all unchanged in what they promise — only D32's "how many
cards start pre-filled" gains a concrete formula, and the interaction fulfilling D32 changed from
an assumed drag to select-then-place.

## Trade-offs

**The last card in a small bank is free by elimination.** At `easy` hints on a 2-blank chart,
placing the one real blank correctly is trivial once every *other* card has an obvious home.
Accepted rather than patched with distractors, for the reason above; noted in `docs/GAME.md` as a
real, not hidden, limitation of the "exactly N cards for N blanks" design.

**Clicking an already-filled blank with nothing held picks that card back up** — an affordance
the approved interaction design didn't explicitly ask for, but without it a learner who places one
card wrong could never correct it short of placing every other card and then being told the whole
puzzle is wrong. Added because the alternative is a real usability trap, not a design purity
concern; every test and screenshot exercising the puzzle uses this path at least once.

**A tiny dashed placeholder barely moves under the shared `emphasisVariants` scale/brightness
treatment** — found at this milestone's own screenshot self-review, not predicted at design time
(the m14b plan flagged this exact risk in advance). The generic 12%-scale, 15%-brightness bump
that reads clearly on a value box (`NumberList.tsx`, `DictTable.tsx`) is nearly invisible on a
small bordered box with no fill. Fixed with a direct ring-and-glow treatment on the targeted
blank's own button (`Flowchart.tsx`'s `BlankableLabel`), layered on top of — not instead of — the
existing dim treatment on every other node, so CLAUDE.md's spotlight rule ("drawn large and
bright... applies to every renderer") holds by actually reading as bright, not merely computing a
transform that happens not to be visible at this scale.
